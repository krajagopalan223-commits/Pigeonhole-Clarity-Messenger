P2P Network & Fallback
Clarity's core strength lies in its decentralized, peer-to-peer network, designed 
for ultimate resilience and privacy. However, a new network needs a robust 
strategy for initial adoption.
P2P Routing: Leveraging 
User Devices
Messages traverse a dynamic 
mesh of active user devices 
(nodes), each contributing to 
routing traffic. This onion-routing 
approach obfuscates 
sender/receiver identities and 
makes traffic analysis extremely 
difficult, even if a node is 
compromised. There's no central 
server to target or surveil.
Cold Start Fallback: 
Community Relays
To address the "cold start" 
problem of limited active nodes, 
Clarity will initially leverage a 
network of geographically 
distributed, privacy-hardened 
Community Relay Servers. 
These relays only handle 
encrypted routing, cannot 
decrypt message content, and 
are operated by trusted, 
independently audited entities.
Phased Transition to Pure P2P
As the user base grows and more peer nodes become available, the 
routing algorithm will automatically reduce reliance on Community 
Relays. The long-term vision is a fully autonomous, user-powered 
network where messages primarily route through other active user 
devices, minimizing any centralized points.

Covert Transport Layer: Steganographic & Proximity 
Channels
Beyond the primary onion-routed relay network, Clarity implements a suite of covert transport mechanisms that allow messages to 
hitchhike inside existing network traffic and propagate across proximity radio channels. These transports are designed for adversarial 
environments where internet access is monitored, throttled, or severed entirely. They are collectively referred to as the Clarity Covert 
Transport Layer (CCTL).
Community Relay Servers (Cold-Start Infrastructure)
During the early network phase, before sufficient peer nodes exist, Clarity operates geographically distributed Community Relay 
Servers (CRS):
CRS nodes handle only encrypted onion routing — they never see plaintext content or metadata
Operated by independently audited entities in strong data-protection jurisdictions (Iceland, Switzerland, Panama)
CRS nodes are explicitly zero-trust: Clarity's cryptographic guarantees hold even if every CRS is compromised
Routing algorithm automatically reduces CRS reliance as peer count grows: P(peer) = min(1, active_peers / 500)
CRS nodes deprecated entirely once peer network reaches ~5,000 active nodes
Packet Hitchhiking — Steganographic Network Transport
Clarity's most advanced evasion capability: embedding encrypted message fragments inside unused or pseudo-random fields of 
existing, innocent-looking network protocols. This makes Clarity traffic indistinguishable from normal internet traffic to deep packet 
inspection (DPI) systems.
Implemented steganographic channels:
TCP ISN Steganography — 4 bytes per SYN packet hidden in the TCP Initial Sequence Number field. Indistinguishable from OS-
generated ISNs via reversible transforms (Murdoch & Lewis, Cambridge 2005). ~32 bits per TCP handshake.
IP Identification Field — 16 bits per packet hidden in the IP ID field. Statistical model of legitimate OS IP ID generation prevents 
steganalysis detection.
HTTPS/TLS Record Padding — Message data fragmented and embedded inside TLS 1.3 record layer padding bytes. Protocol-
compliant per RFC 8446; undetectable without the decryption key.
DNS Query Steganography — Fragments encoded as subdomains of legitimate-looking DNS queries (e.g., a3f9b2c1.cdn.clarity-
cdn.net). Replies carry fragments in TXT records. ~200 bytes per query/response pair.
VoIP/RTP Stream Embedding (TranSteg) — Message data embedded in unused payload space created by transcoding audio to a 
lower-bitrate codec while maintaining original packet size (Mazurczyk & Szczypiorski, Warsaw University of Technology). ~1–4 
Kbps covert channel within a standard VoIP call.
All steganographic channels apply ChaCha20-Poly1305 encryption before embedding — the carrier protocol provides cover, not 
security.
Bluetooth Mesh Transport
In environments without internet access, Clarity routes messages across a BLE mesh formed by nearby devices:
Based on Bluetooth Mesh Protocol v1.1 (Bluetooth SIG, 2023)
Each Clarity device acts as a mesh node, relaying encrypted packets via BLE advertisement flooding
Dual-layer encryption: Clarity's ChaCha20-Poly1305 sits above BLE Mesh's native AES-128-CCM
Message obfuscation: BLE Mesh privacy keys obfuscate source address in packet headers
Replay protection: 32-bit sequence numbers with 24-bit IV index
Routing: Managed flooding with TTL=7 default; Directed Forwarding (v1.1) for high-traffic unicast pairs
Range: ~10–30m per hop; scales with device density
Use cases: RF-jammed environments, underground facilities, air-gapped bridging
Bandwidth: ~1–10 Kbps; latency ~500ms per hop
NFC & RFID Dead Drop Transport
For zero-emission physical proximity exchange — no detectable RF beyond ~10cm:
NFC Dead Drop Protocol:
Sender encrypts message bundle with recipient's public key (standard Clarity E2E)1.
Bundle written to NFC tag (NTAG216, 888 bytes) or transferred via NFC P2P (ISO 18092)2.
Physical tag left at pre-arranged dead drop location3.
Recipient taps tag; Clarity reads and decrypts bundle4.
Tag cryptographically wiped after first successful read (write-lock + counter verification)5.
RFID Covert Channel:
Short fragments (≤64 bytes) encoded into user-writable memory blocks of ISO 15693 RFID tags
Tags appear as ordinary access cards or asset labels
Fragments encrypted and indistinguishable from random data without the Clarity key
Intended for pre-positioned message drops in high-surveillance environments
Security properties: zero network emission, no timing metadata, full deniability (tag contents indistinguishable from random data 
without recipient's private key)
