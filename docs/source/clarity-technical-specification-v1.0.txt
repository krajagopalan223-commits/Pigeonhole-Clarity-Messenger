1. Executive Summary
Clarity Messenger is designed from first principles to provide communications security at the level required 
by intelligence agencies, defense contractors, and high-value targets of nation-state adversaries. Unlike 
Signal — the current industry benchmark — Clarity encrypts not only message content but all associated 
metadata, operates on a fully decentralized network, and incorporates post-quantum cryptographic 
primitives from day one.
Key security properties guaranteed by Clarity:
End-to-end encryption of all message content and metadata
Perfect Forward Secrecy (PFS) on every message, including group conversations
Zero-knowledge authentication: servers never see user credentials or identity
Post-quantum resistance via Kyber-1024 lattice-based key encapsulation
Decentralized relay network: no single point of failure or surveillance
Metadata obfuscation via onion routing, fixed-size packet padding, and timing noise
Design Philosophy
Clarity's architecture follows three core principles:
Assume Compromise — every component is designed assuming all others may be compromised1.
Minimize Trust — no party, including Clarity's own servers, is trusted with plaintext data2.
Defense in Depth — multiple independent security layers ensure no single vulnerability is catastrophic3.

Subsection 3.2 — Rationale for ChaCha20-Poly1305 over AES-
GCM:
ChaCha20-Poly1305 is selected over AES-GCM for the following reasons:
Constant-time implementation: ChaCha20 is inherently resistant to timing side-channels; AES requires hardware AES-NI to 
achieve constant-time execution
Mobile performance: ChaCha20 outperforms AES-GCM on devices without hardware AES acceleration by 30–50%
Nonce misuse resistance: Poly1305 authentication tag provides strong integrity guarantees even under nonce reuse scenarios
Proven track record: Adopted by TLS 1.3, WireGuard, and OpenSSH
Subsection 3.3 — Random Number Generation:
All cryptographic randomness is sourced from OS-level CSPRNGs: /dev/urandom on Linux, CryptGenRandom on Windows, 
SecRandomCopyBytes on iOS/macOS. No application-level entropy mixing is performed. Clarity does not implement its own RNG.

4. Hybrid Encryption Protocol
Clarity uses a dual-layer hybrid key exchange that combines classical elliptic-curve Diffie-Hellman with post-quantum key 
encapsulation. This ensures security against both classical and quantum adversaries simultaneously.
Subsection 4.1 — Session Key Establishment (step-by-step):
Alice generates an ephemeral X25519 keypair: (ek_A_classical, EK_A_classical)1.
Alice generates an ephemeral Kyber-1024 keypair: (ek_A_pq, EK_A_pq)2.
Alice sends both ephemeral public keys to Bob via the relay network (encrypted under Bob's long-term identity key)3.
Bob performs ECDH: shared_classical = X25519(ek_B_classical, EK_A_classical)4.
Bob performs Kyber KEM encapsulation: (ciphertext_pq, shared_pq) = Kyber.Encaps(EK_A_pq)5.
Bob sends ciphertext_pq to Alice6.
Alice decapsulates: shared_pq = Kyber.Decaps(ek_A_pq, ciphertext_pq)7.
Both parties derive the final session key: session_key = HKDF-SHA3-256(shared_classical || shared_pq, salt, 
"ClaritySessionKey")
8.
All subsequent messages in the session are encrypted with ChaCha20-Poly1305 using session_key9.
Subsection 4.2 — Key Derivation Details:
The HKDF derivation uses the following parameters:       - IKM (Input Key Material): Concatenation of X25519 shared secret (32 
bytes) and Kyber shared secret (32 bytes) = 64 bytes total       - Salt: Random 32-byte value exchanged during session initiation       
- Info: ASCII string 'ClaritySessionKey-v1' (domain separation)       - Output length: 32 bytes (256-bit session key)
Subsection 4.3 — Nonce Management:
Each message uses a unique 96-bit nonce derived as: nonce = BLAKE3(session_key || message_counter || timestamp_ms). The 
message counter is a monotonically increasing 64-bit integer. Nonce reuse is cryptographically impossible within a session. 
Sessions are terminated and re-keyed before counter exhaustion at 2^32 messages.

5. Perfect Forward Secrecy
Clarity implements a double-ratchet mechanism inspired by the Signal Protocol but extended to cover group conversations and 
to integrate post-quantum key material into the ratchet state.
Subsection 5.1 — Ratchet Architecture:
The Clarity Double Ratchet consists of two interlocked ratchets:
Diffie-Hellman Ratchet (Asymmetric): Advances on every message exchange round-trip. Each advance generates a new 
ephemeral DH keypair and derives a new root key. This provides break-in recovery (future secrecy) — if an attacker 
compromises the current state, they cannot decrypt future messages once the ratchet advances.
Symmetric-Key Ratchet (Chain Key): Advances on every individual message. Each message derives a unique message key 
from the current chain key via HKDF. The chain key is then advanced and the previous value is deleted. This provides 
forward secrecy — compromise of the current chain key does not expose previous messages.

Subsection 5.3 — Key Deletion:
Clarity uses secure memory wiping (memset_s or equivalent) to overwrite key material before deallocation. On iOS, keys are 
stored in the Secure Enclave where possible. On Android, keys are stored in the Android Keystore with hardware-backed 
protection. Keys are never written to disk in plaintext.
Subsection 5.4 — Blast Radius Analysis:
In the worst-case scenario of a full session state compromise:
Messages before the compromise: Protected by forward secrecy (chain keys already deleted)
The compromised message: Exposed (unavoidable)
Messages after the next DH ratchet advance: Protected by future secrecy
Maximum exposure window: Messages sent between compromise and next DH ratchet advance (≤100 messages or 5 
minutes)

6. Group Messaging Security
Group messaging is the hardest problem in secure communications. Clarity solves it using a TreeKEM-based key distribution protocol that 
provides O(log n) complexity for key operations and full forward secrecy for all group members.
Subsection 6.1 — TreeKEM Protocol:
Clarity's group key management is based on the IETF Messaging Layer Security (MLS) draft standard, using a binary tree structure where:
Each leaf node represents a group member's public key
Each internal node holds a key pair derived from its children
The root node's key is the group encryption key
Adding or removing a member requires updating only O(log n) nodes, not all n members

Subsection 6.3 — Sender Authentication in Groups:
Each group message is signed with the sender's Ed25519 identity key before encryption. Recipients verify the signature after decryption. This 
provides:
Message authenticity: Recipients can verify who sent each message
Non-repudiation within the group: Senders cannot deny sending a message to group members
Note: Deniability to external parties is preserved — the signature is only verifiable by group members who hold the sender's verified public 
key
Subsection 6.4 — Group Admin Operations:
Sensitive group operations (member add/remove, group key rotation, group dissolution) require threshold authorization:
Groups of 2–10 members: Single admin authorization
Groups of 11–50 members: 2-of-3 admin threshold
Groups of 51+ members: 3-of-5 admin threshold
Threshold signatures use a Schnorr multi-signature scheme. No single admin can unilaterally modify large groups.
Subsection 6.5 — Maximum Group Size:
Clarity supports groups of up to 10,000 members. At this scale, key operations remain tractable: O(log 10000) ≈ 13 node updates per member 
change. Message delivery uses a gossip protocol with epidemic broadcast for efficient distribution.

Subsection 7.2 — Message Routing Flow:
Sender's client constructs an onion-encrypted packet with a 5-hop path selected randomly from the relay node pool1.
Each hop is encrypted with the relay node's public key — only that node can decrypt its layer to learn the next hop2.
The innermost layer contains the encrypted message payload, addressed to the recipient's anonymous inbox identifier3.
The final relay node delivers the packet to the recipient's inbox without knowing the sender's identity4.
The recipient's client polls its inbox over a separate anonymized connection, preventing correlation of delivery with receipt5.
Subsection 7.3 — Byzantine Fault Tolerance:
Relay nodes use a PBFT (Practical Byzantine Fault Tolerance) variant for message ordering consensus. The network tolerates up to f = ⌊ (n-
1)/3 ⌋  malicious or faulty nodes, where n is the total number of active relay nodes. With 1,000 relay nodes, the network tolerates up to 333 
simultaneously malicious nodes.
Subsection 7.4 — Node Incentivization:
Relay nodes are incentivized via the Clarity Token (CLR), a utility token distributed as follows:
Nodes earn CLR proportional to verified bandwidth contributed
Proof-of-bandwidth is verified by random client challenges (download test packets)
Minimum stake of 1,000 CLR required to operate a relay node (Sybil resistance)
Slashing: Nodes that fail availability checks or serve malformed packets lose 10% of stake
Subsection 7.5 — Network Capacity:
Target network specifications at launch:
Relay nodes: 500 (bootstrap) →  5,000 (12 months post-launch)
Message throughput: 10,000 messages/second at 500 nodes
Latency overhead vs. direct connection: +80–200ms (onion routing cost)
Geographic distribution: Nodes in ≥30 countries at launch

9. Zero-Knowledge Authentication
Clarity's authentication system allows users to prove their identity to the network without revealing any secret information — 
not even to Clarity's own infrastructure. This is achieved using a Schnorr-based zero-knowledge proof protocol.
Subsection 9.1 — Identity Key Architecture:
Each Clarity user has a three-tier key hierarchy:
01
Identity Key (IK)
Long-term Ed25519 keypair. Never 
leaves the device. Used to sign prekeys.
02
Signed Prekey (SPK)
Medium-term X25519 keypair, rotated 
every 30 days. Signed by IK. Uploaded to 
prekey server.
03
One-Time Prekeys (OPK)
Short-term X25519 keypairs, generated 
in batches of 100. Used once per 
session initiation. Uploaded to prekey 
server.
Subsection 9.2 — Zero-Knowledge Login Protocol:
Client generates a random challenge nonce: c = random_256_bits()1.
Client computes commitment: R = r·G where r is a random scalar and G is the Ed25519 base point2.
Server sends challenge: e = BLAKE3(R || public_key || c || timestamp)3.
Client computes response: s = r + e·private_key (mod curve_order)4.
Client sends (R, s) to server5.
Server verifies: s·G == R + e·public_key6.
If verification passes, authentication succeeds — server learns nothing about private_key7.
This is a Schnorr identification protocol. The server learns only that the client possesses the private key corresponding to the 
registered public key. No password, no secret, and no private key material is ever transmitted.
Subsection 9.3 — Account Recovery:
Clarity does not store recovery codes or backup credentials on any server. Account recovery options:
Multi-device sync: Users can register up to 5 devices; any device can re-authenticate others
Recovery phrase: 24-word BIP-39 mnemonic derived from identity key (stored offline by user)
Social recovery (optional): User designates 3 trusted contacts; 2-of-3 can authorize key reset
Note: If all recovery options are lost, the account is permanently inaccessible. This is by design.
Subsection 9.4 — Prekey Server Trust Model:
The prekey server is explicitly untrusted:
It stores only public keys — no private key material
All prekeys are signed by the user's identity key — tampering is detectable
Clients verify prekey signatures before use — a compromised prekey server cannot perform MITM attacks
Prekey server cannot link prekey requests to specific users (requests are made over anonymized connections)

Options: 1 hour, 24 hours, 7 days, 30 days, or never
Deletion is cryptographic: message keys are securely wiped, rendering ciphertext permanently unrecoverable
Deletion is enforced on all devices in a conversation simultaneously

11. Post-Quantum Readiness
The cryptographic community broadly estimates that a cryptographically relevant quantum computer (CRQC) capable of breaking 
2048-bit RSA and 256-bit elliptic curve cryptography will exist within 10–15 years. Clarity is designed to be quantum-resistant 
from day one, not as an afterthought.

Subsection 11.2 — NIST PQC Standardization:
Clarity's post-quantum primitives are aligned with NIST's Post-Quantum Cryptography standardization process:
Kyber (CRYSTALS-Kyber): Selected as NIST PQC standard (FIPS 203) for key encapsulation
Dilithium (CRYSTALS-Dilithium): Under evaluation for future signature replacement of Ed25519
SPHINCS+: Hash-based signature scheme; being evaluated as a conservative backup
Falcon: Lattice-based signature scheme; under evaluation for performance-critical paths
Subsection 11.3 — Migration Path to Pure Post-Quantum:
Phase 1 (Current — v1.0): Hybrid X25519 + Kyber-1024 key exchange. Classical security maintained; PQ resistance added.1.
Phase 2 (v1.5 — Q2 2026): Replace Ed25519 identity signatures with Dilithium-3. Hybrid signature scheme during transition.2.
Phase 3 (v2.0 — Q4 2026): Pure post-quantum mode available as opt-in. All classical primitives removed from PQ mode.3.
Phase 4 (v3.0 — 2027+): Pure PQ mode becomes default. Classical hybrid mode deprecated.4.
Subsection 11.4 — Harvest Now, Decrypt Later:
A critical threat is 'harvest now, decrypt later' — adversaries recording encrypted traffic today to decrypt once quantum computers 
are available. Clarity's hybrid approach ensures that even traffic recorded today cannot be decrypted by a future quantum 
computer, because the Kyber-1024 layer provides quantum-resistant confidentiality from the first message.

Subsection 14.2 — Signal's Specific Weaknesses:
Signal is the gold standard for consumer secure messaging, but has documented limitations:
Metadata leakage: Signal's servers know who you communicate with, when, and how often. This is confirmed by Signal's own privacy policy and court-ordered 
disclosures.
1.
Centralized infrastructure: Signal operates on AWS. A single legal order or infrastructure failure can disrupt service globally.2.
Phone number requirement: Signal requires a phone number for registration, linking your identity to a telecom provider.3.
No group PFS: Signal's Sender Keys protocol for groups does not provide per-message forward secrecy — a compromised group key exposes all messages 
encrypted under it.
4.
No post-quantum resistance: Signal uses X25519 for key exchange, which is vulnerable to quantum computers.5.
Subsection 14.3 — Clarity's Unique Differentiators:
Three capabilities that no other messaging application currently offers:
Full metadata encryption
Clarity is the only application that encrypts not 
just message content but all metadata — sender, 
recipient, timing, and frequency — using onion 
routing and anonymous identifiers.
Post-quantum hybrid encryption
Clarity is the only consumer messaging 
application with Kyber-1024 post-quantum key 
encapsulation deployed in production.
Group Perfect Forward Secrecy
Clarity's TreeKEM implementation provides per-
message forward secrecy in group 
conversations — a capability no other 
application offers at scale.
